# 面试知识内容判断标准

> 版本：v1.1
> 日期：2026-06-19
> 用途：作为以后新增、修改、审查面试智练内容的持续性判断标准。任何通过 AI 生成的内容改动点，在执行前都必须先仔细阅读并遵守本标准。

## 1. 强制前置要求

任何 AI、脚本或人工在修改本内容库前，必须先完成以下动作：

1. 阅读本标准，确认本次改动是否符合“面试知识内容”的定位。
2. 明确本次改动影响的领域、分类、知识点、manifest 入口和学习路径。
3. 判断每个新增或保留的 topic 是否真的应该成为知识点。
4. 对不符合标准的内容，优先删除、拆分、合并或迁移，不允许为了保留而强行包装。
5. 修改前先看同领域已有内容，保持分类、标题、难度、频率、正文结构一致。
6. 判断本次改动属于“JSON 结构契约变更”还是“知识内容更新”，并按 1.1 的跨项目同步约束处理。
7. 主动站在“从 0 到 1 准备面试的用户”视角检查学习路径、App 首屏顺序、topic 粒度、重复内容和推荐权重，而不是只等待人工指出单个问题。
8. 修改后必须运行内容校验，并做语义抽查；如果是 AI 审查，必须先自行发现和列出问题，再给出整改计划。

如果本标准与单次任务描述冲突，以本标准为准；除非用户明确要求临时改变内容定位。

### 1.1 跨项目同步约束

这里的“结构变更”只指最终 JSON 契约或 schema 发生变化，不指普通知识目录或知识内容变化。判断时以 `schemas/*.schema.json`、`manifest.json` 契约、`domains/*.json` 契约、`topics/*/*.json` 契约和 App/studio 解析模型是否需要变化为准。

JSON 结构契约变更包括但不限于：

1. topic、domain、manifest 中字段更名、删除字段、增加必填字段。
2. 新增字段且 App 或 studio 需要识别、编辑、筛选、渲染、排序、校验或生成该字段。
3. 修改字段类型，例如 string 改 array、number 改 object。
4. 修改字段含义，例如 `recommendWeight` 从推荐权重改成别的语义。
5. 修改枚举值，例如新增 `learningCards.type`、`recallPrompts.mode`、`interviewFrequency` 枚举。
6. 修改嵌套结构，例如 `learningCards`、`rubric`、`learningPaths`、`categories` 的对象结构。
7. 修改文件入口或加载协议，例如 manifest 路径、domain entry 规则、topic 路径规则、draft/staging/production manifest 规则。
8. 修改 schemaVersion/minAppVersion 的兼容策略，或引入旧 App 不能忽略的新结构。
9. 修改内容发布、校验、生成流程中依赖的 JSON 契约。

以下属于知识内容更新，不属于 JSON 结构契约变更：

1. 新增、删除、合并、拆分、迁移 topic，但仍使用现有 topic JSON 结构。
2. 新增、删除、重命名、重排领域或分类，但仍使用现有 domain/manifest JSON 结构。
3. 修改 topic 的标题、摘要、正文、标签、难度、预计学习时间、顺序、推荐权重、面试频率、前置依赖、rubric 文案。
4. 修复错别字、补充解释、改进面试回答、替换模板化追问。
5. 调整知识点归类、排序、权重、频率，只要字段名、字段类型、枚举和解析规则不变。

发生 JSON 结构契约变更时，必须同步检查并更新：

1. 内容仓库：`schemas/`、`docs/content-format.md`、本标准、校验脚本、生成脚本、manifest 示例。
2. App 项目：内容解析模型、缓存/版本兼容逻辑、渲染逻辑、测试，以及 App 项目对应文档。
3. studio 项目：类型定义、表单编辑器、AI 生成模板、校验流程、预览逻辑、发布流程，以及 studio 对应文档。
4. 部署和发布说明：最终部署、内容版本、缓存刷新、schemaVersion/minAppVersion 策略必须参考 App 项目的部署文档，例如 `/Users/yingjunchi/code/mianshi-zhilian-app/docs/deploy.md`。

如果当前执行环境无法访问 App 项目或 studio 项目，不能假装已完成同步；必须在交付说明中明确列出未同步的项目、可能受影响的模块、需要后续执行的检查项。

发生知识内容更新时，通常只需要修改内容仓库，并按 App 部署文档要求更新 `manifest.json` 的 `contentVersion`，运行 `npm run validate` 后发布内容。是否需要改其他项目按需判断：

1. 如果只改现有字段的值，且字段结构、枚举、卡片类型和加载协议不变，通常不需要改 App 或 studio。
2. 如果内容更新暴露出 App 渲染缺陷、studio 表单不支持现有字段、生成提示词不符合新标准，需要同步修对应项目或文档。
3. 如果内容更新改变了长期标准、生成原则或审核口径，需要同步更新内容文档和 studio 的生成/审核说明。
4. 新增/删除领域、分类、topic 时，重点检查 manifest 版本号、topicCount、缓存清理和发布流程；通常不需要发新版 App，除非实际 App 解析或展示出现兼容问题。

## 2. 内容总定位

本仓库是“面试准备知识库”，目标不是泛学习资料、项目包装库、简历辅导库或刷题日程表。

一个合格知识点必须让面试者做到：

1. 直接看完后能说清楚这个概念是什么。
2. 能解释核心原理、关键流程或底层机制。
3. 能回答常见面试问题和追问。
4. 能知道适用场景、边界条件、优缺点和常见误区。
5. 能用结构化语言在面试中复述，而不是只获得零散材料。

内容应服务“从 0 到 1 建立面试八股知识体系”。每个领域都要先覆盖基础高频知识，再覆盖进阶和低频加分项。

AI 或人工审查内容时，不能只看单个 topic 是否写得完整，还必须把自己代入一个真实备考用户，检查：

1. 打开 App 后首屏看到的是否是该领域最基础、最高频、最能建立主线的知识。
2. 用户是否能按当前顺序从易到难学习，而不是一开始就看到低频扩展、生态工具、产品选型或高级架构。
3. 同一领域是否存在重复 topic、合集 topic、空泛 topic 或不该单独成为知识点的内容。
4. 每个 topic 是否真的帮助用户准备面试，而不是只是“看起来有内容”。
5. 排序、频率、权重和学习路径是否共同服务同一个目标：让用户更高效地通过面试。

## 3. 什么可以成为知识点

以下内容可以作为 `topics/*/*.json` 中的独立 topic：

1. 高频八股概念：例如 JVM 内存区域、HashMap、TCP 三次握手、闭包、BFC、AQS。
2. 稳定机制原理：例如 Spring Bean 生命周期、GC Roots、epoll、React Fiber、RAG Pipeline。
3. 可面试复述的流程：例如 HTTPS 握手、类加载流程、DNS 解析流程、请求进入 Spring MVC 的链路。
4. 可比较的技术方案：例如 分布式事务方案、限流算法、HTTP 版本演进、向量索引 Flat/IVF/HNSW/PQ。
5. 稳定工程机制：例如 幂等设计、熔断降级、日志监控、Prompt 注入防护、模型路由。
6. 源码或框架核心能力：例如 ConcurrentHashMap、MyBatis 执行流程、Webpack Loader/Plugin、Vue 响应式。
7. 算法模式和经典算法题：算法领域是唯一例外，可以把 LeetCode 高频题作为知识点。
8. 通用系统设计题：架构领域可以保留秒杀、分库分表、多租户、低代码平台等典型设计题，但必须抽象成通用架构能力。

判断口诀：如果它能被面试官问成“请讲一下 X 的原理/区别/流程/适用场景/常见坑”，通常可以成为知识点。

## 4. 什么不能成为知识点

以下内容不能作为独立 topic：

1. 简历优化、简历 AI 部分包装、项目经历描述、个人项目润色。
2. 面试话术、面试策略、冲刺计划、综合复习、学习路线、每日计划。
3. 场景题合集、模拟面试合集、问题清单合集。
4. 某个厂商、某个模型、某个产品的新闻式介绍，例如单独的“DeepSeek 与开源模型”。
5. 宽泛实践合集，例如“AI 工程化实践”“Node.js 工程实践”“前端最佳实践大全”。
6. 只讲产品选型、工具清单、资料清单、参考链接的内容。
7. 只讲业务案例或个人项目实现，不能抽象出通用知识的内容。
8. 没有稳定边界的新热点、营销概念、趋势预测。

这些内容如果确实有价值，应放到学习路径、补充文档、检查清单，或拆入真正的知识点中。例如：

1. “简历 AI 部分优化”不能作为 topic，可把“RAG 项目如何描述效果指标”放入项目辅导文档，不进入知识库。
2. “AI 综合复习与面试冲刺”不能作为 topic，可作为学习路径或复习计划。
3. “AI 面试场景题”不能作为 topic，其中高质量问题应拆入 RAG、Function Calling、LLMOps 等具体 topic 的 `recallPrompts`。
4. “DeepSeek 与开源模型”不能作为 topic，其中稳定知识可拆成 MoE、推理优化、开源模型部署成本等 topic。

## 5. 知识点粒度标准

一个 topic 应该“小到能独立掌握，大到值得单独学习”。

合格粒度：

1. `HashMap 原理`
2. `ThreadLocal 内存泄漏`
3. `TCP 三次握手与四次挥手`
4. `RAG 文档分块策略`
5. `React Hooks 原理`
6. `分布式锁实现方案`

过大，需要拆分：

1. `Java 新特性`
2. `AI 工程化实践`
3. `前端性能优化全景`
4. `数据库全部知识`
5. `Node.js 工程实践`

过小，需要合并：

1. 单独讲一个工具命令但没有面试考察价值。
2. 单独讲某个配置项但不能形成独立考点。
3. 单独讲某个产品版本特性且没有稳定原理。

## 6. 标题标准

标题必须像“知识点”，不能像“任务”。

推荐标题：

1. `Function Calling 与工具调用`
2. `RAG 基本链路`
3. `向量数据库索引与检索`
4. `MySQL 事务与 MVCC`
5. `Vue 响应式原理`

避免标题：

1. `简历 AI 部分优化`
2. `AI 综合复习与面试冲刺`
3. `AI 面试场景题`
4. `DeepSeek 与开源模型`
5. `某某实战大全`
6. `某某最佳实践合集`

标题写法要求：

1. 中文为主，必要英文术语保留。
2. 中英文之间加空格，例如 `AI 工程化`、`Function Calling`。
3. 不使用“冲刺”“复习”“面试场景题”“话术”“包装”“优化简历”等词。
4. “实战”尽量不用；如果使用，必须指向稳定能力，而不是项目经验。
5. “选型”可以保留，但必须是技术方案知识，例如 `分布式事务方案选型`。

## 7. 分类标准

分类必须按知识体系划分，而不是按学习阶段、面试轮次或简历模块划分。

正确分类方式：

1. Java：基础、集合、JVM、并发、Spring、数据库、中间件。
2. Agent：大模型基础、Embedding 与向量检索、RAG、工具调用与 Agent 架构、LLMOps。
3. 前端：JavaScript、TypeScript、CSS、React、Vue、Node.js、工程化、网络与安全。
4. 网络：TCP/UDP、HTTP/HTTPS、DNS/CDN、WebSocket。
5. OS：进程线程、内存管理、IO 模型、Linux 基础。

错误分类方式：

1. 第一阶段、第二阶段。
2. 初面、二面、HR 面。
3. 简历模块、项目模块、冲刺模块。
4. 场景题、综合复习、面试技巧。

分类排序应遵循：基础概念 -> 核心原理 -> 框架机制 -> 工程问题 -> 架构设计 -> 高级扩展。

### 7.1 App 展示顺序与学习路径标准

内容最终会在 App 中被用户按领域、分类和知识点顺序学习，因此顺序本身就是内容质量的一部分。一个 topic 写得再完整，如果把低频扩展排在高频基础前面，也不算整体合格。

每个领域和分类都必须满足：

1. 默认顺序先讲基础概念，再讲核心机制，再讲框架、工程和架构扩展。
2. 高频基础 topic 不应被低频新特性、生态工具、产品选型或高级扩展挤到后面。
3. `domains/*.json` 中 `categories[].topics` 的列表顺序必须与 topic 的 `order` 字段一致，除非 App 明确不使用 `order` 排序，并已在文档中说明。
4. 同一分类内不应出现重复 `order`。重复 order 会让 App 排序不稳定，导致用户看到的顺序不可控。
5. `interviewFrequency` 与 `recommendWeight` 必须大体一致：high 通常高权重，low 通常低权重。例外必须有明确理由，例如某个 medium topic 是大量后续内容的前置依赖。
6. low 频扩展 topic 不应出现在分类首屏，除非该分类本身就是扩展专题。
7. 如果一个 topic 是某领域主线之外的方向，例如 .NET 客户端、前端跨端、Service Mesh、React Native，应放在独立路线或后置扩展中。
8. 算法领域每个题型分类应先展示题型/数据结构基础，再展示 LeetCode 题。

推荐领域顺序示例：

1. Java：集合/基础 -> JVM -> 并发 -> Spring 核心 -> 数据库 -> 中间件/微服务扩展。
2. Agent：大模型基础 -> Embedding/向量检索 -> RAG -> Function Calling/工具调用 -> Agent 架构 -> LLMOps。
3. 前端：JavaScript 基础 -> TypeScript/CSS -> React/Vue 核心 -> 工程化 -> 架构/跨端扩展。
4. OS：进程线程基础 -> 内存管理 -> IO 模型 -> Linux 基础。
5. Network：TCP/UDP 基础 -> HTTP/HTTPS -> DNS/CDN -> WebSocket。

禁止的排序现象：

1. Java 基础分类中 `Record`、`Sealed Classes`、`Java 新特性` 排在 `HashMap`、`ArrayList` 前面。
2. OS 分类中 Linux 命令和文件权限权重高于进程线程、虚拟内存、IO 模型。
3. 前端分类中微前端、跨端、性能优化全景排在 JS、CSS、React/Vue 核心之前。
4. Agent 分类中多 Agent、MCP 深度排在 Function Calling、RAG 基础之前。
5. 算法分类中 LeetCode 题排在该题型基础讲解之前。

## 8. 正文内容标准

每个 topic 至少应回答 8 个问题：

1. 这个知识点是什么。
2. 为什么会有这个机制或问题。
3. 核心流程或底层原理是什么。
4. 面试官最常问什么。
5. 它和相近概念有什么区别。
6. 适用场景和不适用场景是什么。
7. 常见误区和坑是什么。
8. 如何用一段完整面试回答讲出来。

`learningCards` 排列顺序必须遵循以下规则，校验脚本会检查并扣分：

1. `explain`：概念和核心原理。
2. `diagram` 或 `compareTable`：流程、结构、对比。
3. `code`：需要代码表达的知识点才使用。
4. `interviewAnswer`：标准面试回答。
5. `checklist`：复述要点、排查步骤或答题结构。

`code` 卡位置允许微调（例如紧跟在引用它的 explain 后面），但 `interviewAnswer` 必须在所有 explain/diagram/compareTable/code 之后、`checklist` 之前。

正文禁止：

1. 只有定义，没有原理。
2. 只有清单，没有解释。
3. 只有项目经验，没有通用机制。
4. 大段参考链接或资料列表。
5. “今日笔记”模板。
6. 与 topic 无关的内容串入，例如 Agent 内容里出现 Spring Boot 自动装配。

### 8.1 explain 卡结构标准（难度自适应）

用户可能只听过知识点名称，甚至几乎没有接触过这个 topic；`explain` 的职责是让用户只看本知识点也能建立可复述的机制理解。它不是低价值科普，也不是把面试答案搬进来，而是要把“解决什么问题、核心机制怎么跑、边界和易错点在哪里”讲清楚。话术交给 `interviewAnswer`、对比交给 `compareTable`、代码交给 `code`，**不要互相重复**。卡的数量和深度必须随 `difficulty` 走，而不是统一套一个三段式模板：

| difficulty | explain 卡数 | 结构 |
| --- | --- | --- |
| 1-2（简单/高频基础） | 1 张，紧凑 | 一句话定位 + 核心机制要点 + 一句话点透易错/区别。目标 30 秒激活记忆、补盲点，不写“为什么需要 X”的入门铺垫。 |
| 3（核心机制） | 2 张 | ① 核心机制讲透（为什么这么设计）② 坑 / 边界 / 选型 / 与相似概念区别。 |
| 4-5（高阶疑难） | 2-3 张 | 按机制分层：整体结构/流程 → 难点逐个击破 → 权衡/调优/失败处理。递进在这里才有价值。 |

硬性要求：

1. **标题信息化**：标题直接写这张卡的考点（如“DCL 为什么要 volatile”“自调用导致事务失效”），禁止用“知识全景/核心概念/深入理解/机制演进/选型边界”这类空泛标题。
2. **简单题不注水**：difficulty 1-2 不得为了凑结构拆成多卡或加入门铺垫。
3. **难题讲细**：difficulty 4-5 必须把关键机制、为什么这么设计、失败/边界讲清，达到“几乎不了解这个知识点的人看完也能讲明白”的程度。
4. **不与其他卡重复**：explain 讲“为什么/怎么运作”，不抄 interviewAnswer 的话术、不抄 compareTable 的表格。

### 8.2 图示卡质量标准

`diagram` 或 `animation` 不是装饰卡，也不是为了满足“有图”而随便放一个流程。图示必须降低理解成本，让零基础用户能看出结构、流转、分支、取舍或排查路径。

合格图示必须满足：

1. **节点专属**：节点名称应来自当前 topic 的关键概念、对象、状态、链路或角色，例如 `ClientHello`、`Undo Log`、`Pod`、`Consumer Group`。禁止大量使用 `输入`、`处理`、`输出`、`关键流程`、`边界处理` 这类万能节点。
2. **关系清楚**：连线必须表达真实关系，例如调用顺序、数据流向、状态转移、依赖关系、隔离边界或失败路径；不能只是把正文要点横向排开。
3. **图文一致**：图示标题、节点、`caption`、`fallback` 必须与 topic 标题、summary、tags 和正文主线能对应上，不能跨领域串入无关内容。
4. **兜底可读**：复杂 Mermaid 或动画必须提供 `fallback` 或 `caption`，即使图渲染失败，用户也能读懂图在讲什么。
5. **不替代解释**：图示只帮助理解结构或流程，不能用一张图替代 explain 对机制、边界和误区的解释。
6. **孤立节点先诊断再处理**：Mermaid 中出现没有连线的节点时，不能直接批量删除。先判断它是否是重复定义、是否应该与上一/下一节点补边、是否引用了错误节点、是否已有更清晰的新图替代；只有确认节点无语义价值或已有更好图承接时，才可以删除。
7. **降级链可用**：卡片可使用 `sources`，按 svg 资源或内联 SVG → mermaid 结构图 → text 兜底的顺序降级；`svg.path` 必须位于 `assets/` 且真实存在，`svg.content` 必须是真正的 `<svg...>` 源码，不能把资源路径塞进 content；必须保留可读的 mermaid/text/fallback。
8. **复杂 Mermaid 有边界**：允许 `subgraph`、`stateDiagram`、`sequenceDiagram` 和 5 色板 `classDef`，但禁止 `classDiagram/gantt/pie/journey/erDiagram/mindmap` 与裸 `style` 行。

**按 topic 类型选择图示**：

| topic 类型 | 推荐图示 | 说明 |
|---|---|---|
| 协议/状态机（TCP 握手、Raft、OAuth2、事务状态机） | `mermaid(stateDiagram/sequenceDiagram) + text` | 时序图/状态图已足够 |
| 架构/跨系统（微服务拓扑、数据血缘、CI/CD 流水线） | `mermaid(flowchart+subgraph) + text` | 模块分组和调用链用 subgraph 最合适 |
| 概念/对比/分类（设计模式对比、数据结构选型） | `compareTable` | 对比表足够，不要强行画图 |
| 基础题（difficulty 1-2） | 保持简洁 | 已有简单 flowchart 或对比表保留即可 |

**图解形态适配标准**：

1. SVG、Mermaid、compareTable 都不是天然高级或低级，判断依据只有一个：它是否比其他形态更低成本地讲清当前 topic 的真实机制。
2. 不是每个 topic 都必须有 SVG、Mermaid 或其他 diagram。文字、代码卡、compareTable 已经更清楚时，不要为了“有图”新增图解；判官的推荐形态可以是 `code`、`compareTable`、`text` 或 `none`。
3. SVG 更适合表现空间结构和状态变化：算法数组窗口、双指针移动、DP 表、矩阵、链表指针、树/图遍历 frontier、堆、回溯搜索树、多面板步骤、JVM/缓存/索引/内存引用链、网络包结构等。
4. Mermaid 更适合表达抽象关系：`sequenceDiagram` 表达协议交互，`stateDiagram` 表达状态机，`flowchart/graph + subgraph` 表达架构边界、调用链和数据流。
5. compareTable 更适合概念边界、方案选型和分类对比；不要为了“有图”把对比题硬画成流程图。
6. 不得一味生成 SVG。如果 SVG 只是 Mermaid 节点换皮、没有表达更多信息、文字过密、移动端看不清、维护成本高，应改用 Mermaid、compareTable、text，或在不需要图时移除图解。
7. 不得一味弱化为 Mermaid。已有 SVG 如果表达了空间结构、步骤状态或数据结构细节，不能删除 SVG、不能替换成更弱的 Mermaid 线性链，除非能证明 Mermaid 在语义、可读性和维护性上不差于原 SVG。
8. 算法图解一旦存在，就必须体现题目真实数据结构和推演过程，禁止复用“四个节点换名字”的模板图。DP 题要能看出状态表或状态转移，双指针/滑动窗口题要能看出窗口移动，树/图题要能看出节点关系和遍历 frontier，回溯题要能看出选择树或剪枝。
9. 只要使用 `diagram` 或 `animation`，就必须提供可读的 `fallback`、`caption` 或 text source 兜底；使用 SVG 的 `sources` 还必须保留 mermaid 或 text 降级链。只有 svg path、没有可读兜底的图解不能作为发布态高质量内容。
10. 文本模型不能假装看见图片。图的语义适配可由文本判官评估；重叠、裁切、空白、显示不全、文字过密、字号过小、边线压字等视觉问题必须由渲染 QA 或视觉模型评估。没有视觉报告时，视觉结论只能标记为未核验。

不合格图示包括：

1. 所有 topic 都复用 `输入 -> 状态维护 -> 边界处理 -> 输出答案`。
2. `DDD` 里出现 `TCP` 握手、`RAG` 里出现 `Spring Bean` 生命周期等跨领域污染。
3. 标题叫“结构图解/流程图”，但节点没有当前知识点的专属术语。
4. 图只展示名词堆叠，没有关系、顺序、边界或因果。
5. 用 `topic 标题 -> 领域 -> 分类 -> 标签` 拼出的“关键链路图”。这类图看似相关，实际没有解释机制。
6. **纯线性关键词链假图**：节点即使是本题专属术语，但整图是一条直线（`A -> B -> C -> D -> …`，无分支、无汇合、无状态转移），或终点是“面试结论 / 答题要点 / 总结”这类汇聚节点。判断真假图的关键不在节点是否专属，而在**边是否表达真实机制**（调用顺序、数据流、状态转移、分支、失败路径）。只要是关键词顺次串联、边不承载机制，即为假图，必须重画。

### 8.3 自动质量评分标准

正式发布阶段的内容必须通过结构校验和内容质量评分。质量评分不是替代人工审查，而是把常见低质量问题前置拦截。

`npm run quality:audit` 的最低合格线：

1. 单个 topic 分数必须 >= 90。
2. 单个领域平均分必须 >= 90，且领域内不能存在低于 90 的 topic。
3. 全库总体平均分必须 >= 90。
4. 不允许存在 topic 顺序错误、重复 order、跨领域重复标题等硬性问题。

分数语义（以“用户从不会，到能在面试中灵活运用”为标尺）：

1. **90-94**：最低合格线 = 零基础用户只靠这一篇就能建立机制理解、答出本篇的回忆题、并把知识用到面试回答里。结构完整但教不会人（清单骨架、考题超纲、无场景练习）不算 90。
2. **95-98**：内容优秀，有清晰例子、边界、验证证据、图示和追问，语言完全为本知识点原创，练习能形成场景迁移，读起来专业且顺。
3. **99-100**：接近人工精品，几乎无短板；不仅没踩雷，还能让人觉得解释充分、图文贴合、考核点具体。

评分不再只做“从 100 往下扣”的缺陷扫描，也会检查正向质量证据。没有明显错误但缺少例子、失败路径、验证指标、取舍分析、专属图示或具体 rubric 时，分数会被封顶，不能因为字段齐全就拿 99。自动评分按资深领域评审视角拆成 9 个维度：结构完整性、内容深度、专家证据、讲解清晰度、图示/对比、面试可用性、rubric 评估质量、模板与语言卫生、区分度天花板。90 分不是“没有硬伤”，而是这些维度整体达到真实写得好的水平。

**目标层次（区分度天花板）**：内容深度必须对标真实职级。技术域对标 **P7/P7+（资深/专家）** 的知识储备——difficulty 4-5 要达到源码级机制、架构链路、极端规模与工程权衡的深度，能真正区分资深与专家；difficulty 3 至少要能区分资深；difficulty 1-2 的基础题保持诚实标注、紧凑不注水（拔高基础题等于难度虚标）。非技术域（如自媒体）对标该职业资深从业者的纵深，要有可量化方法、真实数据口径与来源、失败复盘和取舍，不停留在常识科普。一篇题“能筛到哪个职级”由它的 recallPrompts + followUpQuestions 决定：若全部问题只考“是什么/列举”，区分度封顶“仅中级”；difficulty≥3 要具备资深（P7）区分度，必须至少有一条“为什么这样设计而非另一种 / 线上如何排查 / 取舍权衡 / 极端场景如何应对”的深问，且正文能支撑该深问的答案。

评分采用“两遍扫描”：第一遍加载全库建立语料库（跨 topic 句子指纹、领域术语词典），第二遍带语料库上下文逐 topic 评分。反刷分机制包括：

1. **跨 topic 模板句封顶**：任何一句 ≥20 字的句子（剥离代码块后）逐字出现在 ≥4 个 topic 中即判为模板句。含 1 句封顶 94，2 句封顶 92，3 句及以上封顶 88（必不及格）。算法领域的答题脚手架句单独轻罚，但建议按题面改写。
2. **有效字数去重**：explain 和正文总量按“去重后的句子”计算，重复粘贴的句子不增加深度得分；topic 内部句子重复率 >15% 直接扣分并封顶 89，>12% 封顶 94。
3. **取证范围限定卡片正文**：例子、边界、验证、取舍、失败路径、专属词对齐等专家信号只在卡片正文（explain/interviewAnswer/checklist/对比表/图注）中取证；写在 title、tags、summary、rubric 里不算数，杜绝“自己匹配自己”。
4. **维度地板**：90+ 不允许任何核心维度存在明显短板（各维度有最低占比地板，低于地板封顶 89），强维度不能补偿弱维度。
5. **领域术语词典**：由该领域全部 tags 自动构建术语词典；difficulty ≥3 的 topic 卡片正文若一个领域术语都不命中，按跑题/表面化处理；覆盖广（≥6 个跨 topic 术语）记为正向证据。
6. **图表与代码刚性检查**：Mermaid 首行必须是合法图类型声明、不允许重复连线；对比表（含 markdown 形式）不允许空单元格、重复行、两行高度相似、多行所有列取值相同；code 卡 language 与代码内容特征不符、以省略/TODO 占位为主、缺少 highlights 都会扣分。
7. **完成度与可读性**：TODO/待补充/此处省略等占位文案封顶 89；正文（剥离代码后）出现未渲染的 \n/\t 字面量、乱码替换符、未闭合代码围栏、无分段长文（≥380 字无换行）、多个 ≥150 字无停顿长句都会扣分。
8. **重复互抄检查**：explain 卡之间、追问答案之间、recallPrompts 之间相似度过高（Jaccard >0.7-0.8）扣分；explain 与 interviewAnswer 整体重复同样扣分。
9. **正向事实锚点**：具体数字、复杂度、版本号、容量/时延单位等事实证据记为正向信号；95+ 要求语言完全为本知识点原创且几乎无短板。difficulty ≥4 完全没有事实锚点会扣分。
10. **学习闭环自包含**：recallPrompts 考的点必须能从本篇卡片正文学到（词覆盖率过低 = 学完答不出，扣分）；rubric.mustHave 要求的点必须被正文覆盖（否则学完达不到自己定的及格线）。
11. **场景迁移练习**：difficulty ≥3 的非算法 topic，回忆题/追问/面试回答里必须有场景型问题（线上故障、如何排查、怎么选型、什么场景下），否则只能背诵、练不出灵活运用，封顶 94。
12. **清单骨架检测**：explain 卡若成段文字 <60 字、实质性要点（≥18 字）≤2 条、且要点行 ≥5 行，判为“只有清单没有解释”的骨架笔记（标准 §8 明令禁止），扣分并封顶 92。算法领域的步骤列表 + 代码卡形态豁免。
13. **讲练衔接**：interviewAnswer 与 explain 词汇关联度过低（讲的和练的不是一套机制）扣分；过高（互相抄）也扣分。
14. **学习时长真实性**：estimatedMinutes 与去重后内容量的密度超出 35-450 字/分钟区间，按误导学习计划扣分。
15. **rubric 不得内嵌代码**：rubric.mustHave / goodToHave / commonMistakes 命中代码特征（`throw new ...()`、`function`、`=>`、带分号的语句、缩进代码块）即判 P0——rubric 只能是知识点名词短语或自然语句，代码只放 code 卡。
16. **假图检测（线性关键词链）**：mermaid 图若构成单链（每节点入度≤1、出度≤1，无分支/汇合/状态转移）、或终点节点文本命中“结论/要点/总结/面试”，即使节点专属也判为假图扣分。判真假图看边是否承载机制，而非节点是否专属。
17. **区分度天花板**：difficulty≥3 的技术题，若 recallPrompts/followUpQuestions 全是“是什么/列举”、缺“为什么这样设计 / 如何排查 / 取舍 / 极端场景”深问，按区分度不足封顶（只能区分中级，达不到 P7）；difficulty 4-5 必须具备专家（P7+）区分度。基础题（difficulty 1-2）豁免，但不得为凑深度注水或虚标难度。
18. **图解形态非退化**：已有承载真实空间/状态/数据结构信息的 SVG 被删除或替换后信息量变弱、SVG sources 缺少 mermaid/text 兜底、新增 SVG 路径不存在、空间/状态型 topic 被普通 Mermaid 流程链替代，都会扣分或封顶。SVG 不是加分捷径，Mermaid 也不是降级同义词，必须按 topic 机制选择；装饰性或错误 SVG 可以移除，但要用更清晰的文字、表格、Mermaid 或重画图替代。

> 第 15-18 条由 `quality:audit` 分批纳入确定性检测——一次性开启会回溯性判挂存量中的线性串联图、rubric 代码和图解兜底问题，需配合存量整改逐步收紧，不要在未清理存量前直接加成硬门禁。agent 按 `docs/nine-dimension-scoring.md` 复查时也应对照这几条。

评分重点覆盖：

1. 内容深度：explain 数量、正文量、机制/边界/误区是否讲清。
2. 易理解性：是否有清晰图示或对比表，图示是否专属、相关、可兜底。
3. 面试可用性：interviewAnswer 是否有结论、机制、边界和至少 2 条具体追问。
4. 评估有效性：recallPrompts 是否像真实面试题，rubric 是否专属当前知识点。
5. 模板污染：是否出现“深入理解续”“核心概念”“建议结合实际项目”“理论和实践脱节”“关键行”等占位文案。
6. 语言自然度：是否像连续写成的知识讲解，禁止明显拼接感、补丁句、占位句、跨 topic 重复套话。
7. 图示质量：是否存在自动拼接图、孤立节点误处理、fallback 与节点不一致、节点与 topic 只有表面关联等问题。
8. 跨领域一致性：是否与其他领域重复、边界不清或混入无关内容。
9. 正向证据密度：是否能看到具体例子、真实场景、失败路径、验证/排查指标、工程取舍、专属术语覆盖和非模板化 rubric。

### 8.4 静态门禁与 agent 复查

静态脚本只能拦截结构、模板、重复、覆盖率和正向证据，不能可靠判断事实正确性、讲解顺序是否符合认知规律、专家口吻是否真实。因此发布态 topic 的新增、大改或质量不确定时，由维护者或 agent 按 `docs/nine-dimension-scoring.md` 复查。

默认规则：

1. CI 不配置 LLM key、模型或 provider。
2. CI 只运行 `npm run ci:static`，即脚本语法检查、`validate`、`quality:scan`、`quality:audit`。
3. 维护者或 agent 复查时，对照 `docs/nine-dimension-scoring.md` 的 9 维口径与反刷分规则，重点处理：事实正确性、认知顺序、专家口吻、自包含闭环、面试可用性、难度匹配、区分度天花板、rubric 与图示卫生、图解形态适配与非退化。
4. 静态 `90` 分只是提交和同步前的最低门槛；目标分 `95+`，且没有 9 维短板、事实问题、图解退化或格式问题。
5. 每个本地 clone 必须运行一次 `npm run hooks:install` 才会启用 `.githooks/pre-commit`；当前 hook 只做暂存 topic 的 JSON 和静态质量分门禁。

事实正确性、版本、复杂度、协议/API 行为等容易过时的事实，由 agent 复查时通过官方文档、标准规范、源码文档、论文或 release notes 核对，发现 wrong/outdated 必须修正。rubric 三项不得内嵌代码（代码进 code 卡）；diagram 不得是纯线性关键词链或终点为"面试结论"类汇聚节点的假图，边必须承载真实机制；已有好 SVG 不能被弱化成 Mermaid，Mermaid 已足够清晰时也不能为了"升级"强行 SVG。

## 9. 面试可用性标准

内容必须让面试者能“看完就能答”。

一个 topic 的 `interviewAnswer` 应满足：

1. 第一段先给结论。
2. 第二段解释原理或流程。
3. 第三段补充场景、优缺点或常见坑。
4. 如果是高阶题，最后补充追问点。

错误示例：

1. “建议结合实际项目理解。”
2. “最常见的坑是理论和实践脱节。”
3. “这个问题要看具体情况。”
4. “可根据业务选择不同方案。”

这些句子太空泛，不能帮助面试者作答。必须替换成具体知识点的专属表达。

## 10. recallPrompts 标准

`recallPrompts` 应用于训练复述，不是随便列问题。

合格问题：

1. 能直接模拟真实面试问题。
2. 对应正文中的核心知识。
3. 有明确评价标准。
4. 难度与 topic 难度一致。

示例：

1. `HashMap 为什么线程不安全？JDK 1.7 和 JDK 1.8 的问题有什么不同？`
2. `TCP 为什么需要三次握手，两次不行吗？`
3. `RAG 中 chunk size 过大或过小分别有什么问题？`
4. `React Hooks 为什么不能写在条件语句里？`

不合格问题：

1. `你在项目中怎么用这个技术？`
2. `你遇到过什么问题？`
3. `请综合复习本章内容。`
4. `这个知识点有什么注意事项？`

项目类追问可以保留，但必须具体，例如：`如果线上出现 ThreadLocal 导致的内存泄漏，你会如何定位？`

## 11. rubric 标准

`rubric` 是评分标准，必须专属于当前知识点。

`mustHave` 应包含：

1. 必须说出的定义或结论。
2. 必须解释的核心机制。
3. 必须覆盖的关键流程或对比点。

`goodToHave` 应包含：

1. 源码细节。
2. 边界条件。
3. 实际排查经验。
4. 性能或架构权衡。

`commonMistakes` 应包含：

1. 本知识点特有误区。
2. 常见混淆点。
3. 面试表达上的硬伤。

禁止写：

1. `理论和实践脱节`
2. `没有结合项目`
3. `回答不够深入`
4. `不了解原理`

除非后面跟着当前知识点的具体表现。

`mustHave` / `goodToHave` / `commonMistakes` 的每一项只能是知识点描述短语或自然语句，**禁止内嵌代码片段**（如 `throw new UnsupportedOperationException();`、`function`、`=>`、带分号的语句或缩进代码块）。需要代码示例时放进 `code` 卡，不要塞进 rubric——这是 AI 生成器的高发 bug，逐条检查。

## 12. difficulty 标准

`difficulty` 表示理解难度，不表示推荐优先级。

1. `1`：简单定义、简单编码、入门题。例如 两数之和、进程线程基本区别。
2. `2`：基础高频，要求能说出主要区别或常规流程。例如 ArrayList、TCP/UDP、盒模型。
3. `3`：核心机制，要求能解释原理和常见追问。例如 ThreadLocal、MVCC、Promise。
4. `4`：高阶机制，要求能讲源码、架构链路或复杂权衡。例如 AQS、React Fiber、RAG 评估。
5. `5`：综合设计或疑难排查。例如 秒杀系统、多 Agent 协作、大规模性能诊断。

注意：

1. 高频不一定高难。
2. 低频不一定低难。
3. 不要为了显得高级，把基础题设成 4 或 5。

`difficulty` 是“理解难度”，与“目标职级纵深”是两件事，不要混淆：

1. **不要靠拔高 difficulty 来对标 P7**。基础题（如 TCP/UDP、两数之和）即使写给 P7 候选人看，difficulty 仍是 1-2；它的价值是快速激活记忆，不是区分资深。拔高基础题的 difficulty 等于难度虚标。
2. **P7/P7+ 的纵深体现在 difficulty 4-5 的题写得有多透**，而不是把所有题都标成 4-5。技术域必须有足够数量的 difficulty 4-5 题（源码级机制、架构权衡、极端规模、疑难定位）来撑起资深/专家区分度；非技术域按对应职业的资深纵深要求。
3. difficulty 4-5 的题如果只停留在“是什么/列举”、缺机制与权衡，是**深度不足或难度虚标**，按 §8.3 区分度维度扣分，而不是降低 difficulty 蒙混。

## 13. interviewFrequency 标准

`interviewFrequency` 表示真实面试出现概率。

`high`：

1. 多数目标岗位都会问。
2. 属于该领域基础核心。
3. 不掌握会明显影响通过率。

`medium`：

1. 常见追问。
2. 特定方向或中高级岗位常问。
3. 掌握后能明显加分。

`low`：

1. 方向相关或岗位相关。
2. 更偏扩展、产品、生态或高级经验。
3. 可以作为加分项，但不是基础通关必备。

禁止出现整个领域几乎都是 low，除非该领域本身不是面试主线。比如 .NET 后端里 async/await、DI、中间件、认证授权不应全部 low。

## 14. recommendWeight 标准

`recommendWeight` 表示推荐学习优先级，应综合频率、基础性和依赖关系。

建议范围：

1. high：85-100。
2. medium：70-88。
3. low：50-75。

可例外提高的情况：

1. 某 topic 是后续大量内容的前置知识。
2. 虽然频率 medium，但能串起一类题。

例外提高必须能解释清楚，不能只因为内容“看起来高级”或“写得多”就提高权重。

必须降低的情况：

1. 产品生态型内容。
2. 单一框架扩展点。
3. 厂商实现细节。
4. 热点但不稳定内容。
5. 低频新版本特性，例如不是多数岗位必问的语法糖或版本增强。
6. 跨端、客户端、Service Mesh、多 Agent、低代码等方向性扩展，除非当前领域就是这些方向。

权重与频率自检规则：

1. `high` topic 通常不应低于 75；低于 75 时必须检查是否误标 high 或权重过低。
2. `low` topic 通常不应高于 85；高于 85 时必须检查是否误标 low 或权重过高。
3. 同一分类首屏不应同时出现多个 low 频 topic。
4. 如果 App 使用 `recommendWeight` 影响默认展示顺序，必须保证权重不会破坏“从基础到高级”的学习路径。

## 15. 算法领域例外规则

算法领域允许题目成为知识点，因为算法面试的准备天然依赖题型训练。

但算法 topic 必须包含：

1. 题意和输入输出。
2. 核心思路。
3. 为什么使用该数据结构或算法。
4. 时间复杂度和空间复杂度。
5. 边界条件。
6. 可运行代码。
7. 常见变体和追问。

算法分类应按题型和数据结构划分，不按 LeetCode 编号段划分。

## 16. 架构领域例外规则

架构领域可以保留典型系统设计题，但必须满足：

1. 不是个人项目介绍。
2. 能抽象为通用系统设计能力。
3. 包含核心组件、数据流、瓶颈、权衡、降级和扩展方案。
4. 能回答“为什么这样设计，而不是另一种方案”。

可以保留：

1. 秒杀系统设计。
2. 分库分表方案。
3. 多租户 SaaS 架构。
4. API 网关设计。
5. 低代码平台核心架构。

不能保留：

1. 我的项目怎么包装。
2. 某公司业务系统复盘。
3. 简历项目亮点提炼。

## 17. 新增 topic 决策流程

新增 topic 前必须逐项判断：

1. 它是否是稳定知识，而不是任务、计划、话术或热点。
2. 它是否能独立学习和独立复述。
3. 它是否有明确分类。
4. 它是否和已有 topic 重复。
5. 它是否能支撑至少 3 个真实面试问题。
6. 它的难度、频率、权重是否合理。
7. 它是否能写出专属 rubric，而不是泛化评价。

如果任意一项不满足，不要新增 topic。应选择合并、拆分、迁移到文档或放弃。

## 18. 修改已有 topic 决策流程

修改已有 topic 前必须判断：

1. 原 topic 是否应该继续作为知识点。
2. 标题是否准确。
3. 分类是否正确。
4. 是否存在重复 topic。
5. summary 是否自然、准确、无残缺。
6. learningCards 是否覆盖核心原理。
7. recallPrompts 是否真实可问。
8. rubric 是否专属。
9. 难度、频率、权重是否匹配。
10. 它在 App 中的展示位置是否合理，是否会挤占更基础、更高频的知识点。
11. 它是否与同领域其他 topic 重复、重叠或边界不清。
12. 它是否应该拆分、合并、迁移到学习路径或删除，而不是继续润色。

如果 topic 本身定位错误，优先删除或迁移，而不是只润色正文。

## 19. AI 生成内容的特殊要求

所有 AI 生成的改动必须额外遵守：

1. 执行前明确声明已阅读本标准。
2. 不允许批量生成看似完整但实际空泛的 topic。
3. 不允许使用模板化废话填充正文、追问或评分标准。
4. 不允许把用户提到的任何词都直接变成知识点。
5. 不允许把“简历、项目、面试策略、冲刺复习”写入 topics。
6. 不允许用热点词替代稳定知识结构。
7. 不允许混入其他领域内容。
8. 不允许只改标题不改内容定位。
9. 不允许跳过 schema 校验和语义抽查。
10. 不允许在发生 JSON 结构契约变更时只修改内容仓库，而不检查 App、studio 及其对应文档。
11. 不允许只根据用户指出的单个截图或单个 topic 修补局部问题；必须主动扩展检查同领域和相邻领域是否存在同类问题。
12. 不允许只用关键词扫描证明内容合格；必须做“用户学习路径”和“App 首屏展示”的语义审查。
13. 不允许让人工逐个指出显而易见的问题。AI 审查时必须自行检查排序、重复、粒度、权重、频率、分类和跨领域污染。
14. 如果发现标准本身无法约束某类问题，必须提出标准补强建议，而不是继续按不完整标准机械执行。
15. 生成器不得自动注入通用 `code.highlights`、`interviewerFocus`、`commonMistakes` 或 explain 学习脚手架。拿不到当前 topic 的真实代码语义、机制边界和专属误区时，宁可留空或生成待办报告，也不要写“入口/结构行”“学透这题的抓手”“回答不够深入”这类模板。
16. `explain` 只能承载机制理解，不得生成“追问落点”“复述校验”“必须讲透的主线”等面试评分/练习指令；这些内容应分别进入 `interviewAnswer.followUpQuestions`、`checklist` 或 `rubric`。

AI 执行内容生成时，应先输出或内部形成“topic 是否合格”的判断，再修改文件。

### 19.1 AI 主动发现问题流程

当用户要求“评估内容是否符合标准”“检查是否达标”“看看顺序是否合理”“审查内容质量”时，AI 必须主动执行以下流程：

1. 读取 `docs/knowledge-content-standard.md` 和相关 `docs/content-format.md`。
2. 跑结构校验：`npm run validate`。
3. 全域扫描 manifest、domain、topic，列出每个领域的分类顺序和每个分类的 topic 顺序。
4. 检查同一分类内：
   - topic 列表顺序是否与 `order` 一致。
   - 是否有重复 `order`。
   - high 频 topic 是否被低权重压低。
   - low 频 topic 是否权重过高或排在前面。
   - 是否有“全景、综合、其他、新特性、实战、最佳实践”等过泛标题。
   - 是否有标题相近或内容重复 topic。
5. 站在用户视角检查每个领域首屏：
   - 新手第一屏看到这些内容，是否能建立面试主线？
   - 是否从易到难？
   - 是否先学基础再学高级扩展？
6. 对发现的问题给出整改计划，按优先级排序，不只列命中关键词。
7. 如果发现是标准缺失导致问题反复出现，必须同时建议更新标准和校验脚本。
8. 评估类任务除逐篇判定外，必须产出**跨域质量分布与优先级热力图**：列出每个领域的整体水平、问题集中点和先修顺序，并显式区分“自动门禁通过”与“内容真达标”——自动分达 90 不等于达到 P7 区分度，模板污染、假图、区分度不足都可能在 90 分之上仍然存在。优先级要落到“先修哪些域、哪些是 P0 重写、哪些是批量清理”，而不是停在域级评语。

   这张地图不需要手工再审：`npm run quality:audit` 已输出 `Domain priority (worst first)` 段（JSON 模式见 `result.domainPriority`，按域分升序 + P0/P1/P2 tier + 跌破阈值篇数），直接给出"哪个域最烂、先动哪"。它替代了人工审计的跨域排名；逐篇的区分度、假图、事实正确性由 agent 按 `docs/nine-dimension-scoring.md` 复查把关。两者合起来，常规质量评估不再需要一次性人工通读全库。

可使用的全域审查脚本：

```bash
node - <<'NODE'
const fs = require('fs');
const manifest = JSON.parse(fs.readFileSync('manifest.json', 'utf8'));
for (const de of manifest.domains) {
  const d = JSON.parse(fs.readFileSync(de.entry, 'utf8'));
  console.log(`\n## ${d.id}`);
  for (const c of d.categories) {
    const seen = new Map();
    let prev = null;
    for (const ref of c.topics) {
      const t = JSON.parse(fs.readFileSync(ref, 'utf8'));
      if (prev && prev.order > t.order) {
        console.log(`ORDER_DESC ${c.id}: ${prev.title}(${prev.order}) -> ${t.title}(${t.order})`);
      }
      if (seen.has(t.order)) {
        console.log(`DUP_ORDER ${c.id}: ${t.order} ${seen.get(t.order)} / ${t.title}`);
      }
      if (t.interviewFrequency === 'low' && t.recommendWeight >= 85) {
        console.log(`LOW_HIGH_WEIGHT ${c.id}: ${t.title} w=${t.recommendWeight}`);
      }
      if (t.interviewFrequency === 'high' && t.recommendWeight < 75) {
        console.log(`HIGH_LOW_WEIGHT ${c.id}: ${t.title} w=${t.recommendWeight}`);
      }
      if (/全景|综合|其他|新特性|实战|最佳实践/.test(t.title)) {
        console.log(`BROAD_TITLE ${c.id}: ${t.title}`);
      }
      seen.set(t.order, t.title);
      prev = t;
    }
  }
}
NODE
```

## 20. 内容质量验收

每次改动后必须检查：

1. `npm run ci:static` 通过；快速局部检查时至少运行 `npm run validate`。
2. manifest 的 topicCount 与实际文件数一致。
3. domain 分类引用的 topic 文件存在。
4. topic 的 `id`、`domain`、`category` 一致。
5. 同一分类内 topic 列表顺序与 `order` 一致，且没有重复 `order`。
6. `interviewFrequency` 与 `recommendWeight` 大体匹配，没有明显 low 频高权重或 high 频低权重。
7. App 首屏顺序符合从基础到高级、从高频到低频的学习路径。
8. 没有不该作为 topic 的标题。
9. 没有模板化废话。
10. 没有错别字、残句、串入其他领域内容。
11. 没有重复 topic 或边界不清的合集 topic。
12. 每个新增或大改 topic 都能回答至少 3 个真实面试问题。
13. 若发生 JSON 结构契约变更，已同步更新内容文档、App 项目、studio 项目，以及两个项目对应文档；若当前无法访问相关项目，已明确列出未同步项和后续检查项。
14. 若只是知识内容更新，已更新 `manifest.json` 的 `contentVersion`，并判断是否需要同步其他项目或文档。
15. 高频 topic 的 `interviewAnswer` 能读出“30 秒结论 -> 核心机制 -> 追问边界”的层次。
16. 运行结构化质量扫描 `npm run quality:scan`，确认没有模板化空话、前端通用追问、占位式追问答案或正文行内编号残留。
17. 运行内容质量评分 `npm run quality:audit`，确认单 topic、单领域和全库总体均达到 90 分以上。
18. 若新增、大改或不确定发布态 topic 的语义质量，按 `docs/nine-dimension-scoring.md` 复查 9 维短板、事实问题、图解退化或格式问题。
19. 图示必须逐张检查：节点是否专属、关系是否清楚、是否和 topic 相关、fallback/caption 是否能解释图意，不能只检查 Mermaid 语法是否通过。

建议附加检查关键词：

```text
简历
综合复习
面试冲刺
场景题
话术
个人项目
最常见的坑是理论和实践脱节
建议通过实际项目验证理论
今日笔记
```

出现这些词不一定全部错误，但必须人工确认它们是否违反本标准。

## 21. App 展示顺序验收标准

每次内容改动后，除了运行 schema 校验，还必须从"新用户从 0 到 1 准备面试"的视角检查 App 首屏展示顺序。

### 21.1 学习路径顺序原则

每个领域必须遵循：基础概念 -> 核心原理 -> 框架机制 -> 工程问题 -> 架构设计 -> 高级扩展。

具体要求：

1. 高频基础 topic 必须排在低频扩展 topic 前面。
2. 同一分类内 `domain.categories[].topics` 列表顺序必须与 topic `order` 字段一致。
3. 如果 App 不按 `order` 排序，必须在标准中明确 App 使用哪个字段排序。

### 21.2 interviewFrequency 与 recommendWeight 一致性

`interviewFrequency` 与 `recommendWeight` 必须大体一致：

| interviewFrequency | recommendWeight 范围 | 说明 |
|---|---|---|
| high | 85-100 | 高频核心 topic，应排在首屏 |
| medium | 70-88 | 常见追问或特定方向 |
| low | 50-75 | 扩展或加分项 |

可例外提高的情况：

1. 某 topic 是后续大量内容的前置知识（如基础概念 topic）。
2. 虽然频率 medium，但能串起一类题。

必须降低的情况：

1. 产品生态型内容。
2. 单一框架扩展点。
3. 厂商实现细节。
4. 热点但不稳定内容。

### 21.3 排序硬性规则

以下规则必须满足，否则视为验收不通过：

1. high 频核心 topic 不应低于 75 权重，除非该 topic 是低优先级补充。
2. low 频扩展 topic 不应高于 85 权重，除非是大量内容的必要前置依赖。
3. 禁止同一分类内出现重复 `order` 值。
4. 同一分类内 topic 必须按 `order` 升序排列。

### 21.4 验收检查清单

每次验收必须检查：

1. 每个领域首屏是否从最基础、最高频、最能建立面试主线的内容开始。
2. 是否存在 low 频高权重、high 频低权重的异常情况。
3. 是否存在重复 order、列表顺序与 order 冲突的问题。
4. 是否有低频扩展内容挤到高频核心内容前面。
5. `npm run validate` 通过。

### 21.5 验收命令

运行全领域顺序/权重异常扫描：

```bash
node - <<'NODE'
const fs = require('fs');
const manifest = JSON.parse(fs.readFileSync('manifest.json', 'utf8'));
for (const de of manifest.domains) {
  const d = JSON.parse(fs.readFileSync(de.entry, 'utf8'));
  for (const c of d.categories) {

      }
      if (seen.has(t.order)) {
        console.log(`DUP_ORDER ${d.id}/${c.id}: ${t.order} ${seen.get(t.order)} / ${t.title}`);
      }
      seen.set(t.order, t.title);
      if (t.interviewFrequency === 'low' && t.recommendWeight >= 85) {
        console.log(`LOW_HIGH_WEIGHT ${d.id}/${c.id}: ${t.title} w=${t.recommendWeight} ${ref}`);

        console.log(`HIGH_LOW_WEIGHT ${d.id}/${c.id}: ${t.title} w=${t.recommendWeight} ${ref}`);
```

## 22. 最终判断

一个内容改动只有同时满足以下条件，才算合格：

1. 它是面试知识，不是面试周边任务。
2. 它能让面试者直接学习并掌握八股知识。
3. 它能被独立复述和独立评估。
4. 它在领域、分类、顺序中位置合理。
5. 它的难度、频率、权重可信。
6. 它没有空泛模板、错别字、串入内容和重复污染。

如果无法判断，默认不要新增 topic；先把内容放入整改计划或补充文档，等人工确认后再进入正式知识库。
